    AWS-MMS · Automatic Weather Station Maintenance Management System

    How the app is wired

    AWS-MMS is a self-hosted web app for maintaining weather stations that the organization runs for client organizations in several countries. Clients request work and sign it off. Staff plan visits, record them on a phone with or without signal, and produce signed reports.

    This page is the developer's map of the system: services, data, events, flows, configuration and the decisions behind them. Each build phase updates it. Requirements live in the planning documents linked in each section's Sources line.

    Architecture

    Planned

    Five FastAPI services, split by business capability, behind Nginx. One MongoDB replica set with a database per service, Kafka for events between services, Redis for jobs and leases, and SeaweedFS for files. Everything runs with Docker Compose on the organization's own servers.

    Sources: TRD §1, §2 · ADR-1 to ADR-10

    Rules the architecture depends on

    These are enforced by tests in CI (TP "Rule-enforcement tests"). Breaking one is a bug, not a style choice.

    1. Never access another service's database. Call its /internal/* endpoint with a service token, or consume its events. Modules inside operations share its database.
    2. Every state change goes through the domain state machine and the outbox, in one Mongo transaction. Request handlers never produce to Kafka directly. The relay runs only under the service's Redis leader lease.
    3. Org scoping lives in the repository layer. A client's queries are always merged with their org_id (owner_org_id for stations, current_org_id for sensor units).
    4. Out-of-scope records return 404, not 403 (ADR-16).
    5. Viewers never mutate. Every mutating route uses require_roles(...) without viewer.
    6. Internal comments, draft reports, staff-only documents and config versions are filtered out for clients in the repository layer. Files start staff-only.
    7. domain/ imports no FastAPI, Mongo or Kafka.
    8. Times are stored in UTC; each station's IANA time zone is for display.
    9. IDs are UUIDv7, generated on the client for anything created offline. Sync operations carry idempotency keys (op_id).
    10. The audit collection is insert-only and hash-chained.
    11. Finalized visit-report versions are immutable; a change reopens the report as a new version.
    12. Mongo queries are built from typed values only.

    Passwords and throttling

    • Argon2id (argon2-cffi, time ≥ 3, memory ≥ 64 MiB).
    • At least 10 characters, checked against a built-in list of common passwords and the HIBP range API (only 5 hex characters of the SHA-1 leave the server, padded). If HIBP is unreachable the local file is used (AUTH_BREACHED_FILE); with no file the password is accepted and auth_breached_check_unavailable_total counts it (T1).
    • 5 failures per email → locked for the rest of a 15-minute window, keyed by the hash of the normalized email whether or not the account exists. Nginx adds the per-IP limit. Wrong password and unknown email give the same 401 body.
    • A successful reset revokes all refresh tokens and every access token issued before it. Changing the password in My profile signs out the other devices and keeps this one.
    • Registering an email that already has an account answers exactly like a new registration and changes nothing.
    • Signing keys rotate yearly: a new kid joins JWKS; services cache JWKS in Redis for 10 minutes and refetch on an unknown kid.

    Offline PIN session (staff)

    • Set on first "prepare for field": a 4–6 digit PIN.
    • Dexie meta stores the profile, a PBKDF2-SHA-256 verifier (310,000 iterations, random salt) and offline_until. No token is ever stored.
    • No signal and no access token → /unlock. Five wrong PINs turn offline unlock off until the next online login; data is kept.
    • Sync still needs a successful /refresh. Logout removes the profile and bundles; queued work stays for the same user.
    • Clients have no offline session.

    Requests

    In progress · Phase 3 W8 and W9 built

    Derived status (domain/requests/state.py)

    def derive_status(req, visits) -> Status:
    # Only while req.status in {assigned, scheduled, in_progress, client_review}
    live = [v for v in visits if v.status != "cancelled"]
    if any(v.status == "started" for v in live):
        return IN_PROGRESS
    if any(v.status == "planned" for v in live):
        return SCHEDULED
    ended = [v for v in live if v.status == "ended"]
    if not ended:
        return ASSIGNED
    latest = max(v.ended_at for v in ended)
    if any(v.additional_visit_required for v in ended if v.ended_at == latest):
        return ASSIGNED                         # the most recent visit asks for another
    if any(v.report_status != "final" for v in ended):
        return IN_PROGRESS                      # awaiting a visit report
    if req.rework_since and not activity_after(ended, req.rework_since):
        return ASSIGNED                         # client rejected; nothing new since
    return CLIENT_REVIEW
    • Parallel visits: the status follows the busiest visit.
    • Report reopened in Client Review → In progress; reminders and auto-close stop. After Closed the request stays Closed and the close-out report is regenerated.
    • Cancel cancels planned visits in the same transaction; a started visit's work is still accepted.

    As built (W6, documents path)

    PieceWhat it does
    UploadsPOST /uploads is idempotent by media_id (made on the device, rule 9). The record is inserted first and the multipart upload is created after, so a crash between the two is repaired by the next call. The same file chosen again after a reload (same person, owner, size and SHA-256) joins the open upload (resumed: true) and sends only the missing parts. The store is the truth: ListParts says what has arrived, and complete takes no part list, so a client that lost its ETags or its place cannot corrupt the file.
    CompleteChecks every part against the announced size (a presigned URL cannot enforce it): missing parts are the client's to send (409 incomplete_upload with the numbers), a part that is extra or the wrong size aborts the upload and fails the record (size_mismatch). Then it joins the parts, confirms the object size and queues the checks. Repeating it returns the stored result.
    Checks (process_media)One pass over the stored object: SHA-256 against the announced checksum, magic bytes against the name (.pdf must start %PDF-, Office files are ZIP or OLE, text files have no NUL), and the virus scan. Infected, corrupt or mismatched files become failed and are deleted from the store. A scanner or store that cannot be reached puts the file back to uploaded and the job retries; a file is never ready without a scan result (clean, or skipped where the scan is off).
    Virus scan (W6-4)MEDIA_SCAN_MODE=clamd streams the file to ClamAV (INSTREAM; the stack's clamav service raises the 25 MB default to 256 MB). off is for hosts too small for ClamAV (TRD T8: staging) and is refused when MEDIA_ENVIRONMENT=production.     Cronabort_stale_uploads (daily: open uploads older than 48 h are aborted so the store frees their parts, and marked failed) and reconcile (every 5 min: re-queues files stuck in uploaded for 15 min, and puts back files whose worker died in processing). purge_originals arrives with images and video.

    Audit chain

    • Consumer group audit reads every mms.*.events topic and skips notification-only events (calibration.due_digest, request.review_reminder, report.finalize_reminder, visit.sync_conflict).
    • Each append assigns seq = last_seq + 1 and hash = SHA-256(prev_hash ‖ canonical(record)), updating audit_state in the same transaction. The chain order is the commit order, serialized on the head document (TRD 2.1 §12; it replaced a single writer task and gives the same guarantee with every worker consuming). Duplicates are dropped by processed_events and _id = event_id.
    • Canonical form: sorted keys, no spaces, UTF-8, times as UTC ISO 8601 with milliseconds.
    • An event that fails five times goes to mms.dlq.audit. To replay after a fix, stop platform and reset the audit group's offsets (dead letters are skipped, not committed to processed_events, so a replay applies them once).
    • The audit Mongo user can only find and insert on audit_events. No API updates or deletes records.
    • verify() recomputes the chain and reports the first broken seq, including a deleted tail (the head no longer matches). The admin route POST /api/v1/audit/verify and the weekly cron come with the audit viewer (Phase 7).
    • A contract test checks that every AUD-1 action maps to event types, and that every auth event type has a schema and is mapped.

    Maintaining these docs

    This page is part of the definition of done: a phase isn't closed until this page describes what it built. It must stay readable straight from disk, with no server, no build step and no network.

    Every phase

    1. Update Build status: phase badge, the "What exists" table, and the section badges and sidebar dots (dot built / dot progress).
    2. Replace designed shapes with built ones: schemas from the Pydantic models, routes from OpenAPI, events from mms_common.events, settings with their real env var names.
    3. Add the diagrams chosen from Suggested diagrams by phase, and update any diagram the phase changed.
    4. Record new decisions in Decisions and the source document.
    5. Add a Changelog entry.
    6. Open the page in a browser, in light and dark, and check that no diagram shows "could not be drawn".

    If the code and the TRD disagree, fix one of them in the same change. This page describes the code; the TRD describes the design.
