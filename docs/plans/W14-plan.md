# Phase 5 · W14 plan: the outbox, `/sync`, conflicts and resumable uploads

Proposed 2026-10-22, after W13 (#74 to #78, all green, not yet merged). **Questions answered 2026-10-22** (section 8): all four proposed defaults stand. The screens (section 5) are drawn as boards and approved before slices 3 and 4 are built, as for W13; slices 1 and 2 have no screens and start first.

Delivers OFF-2 (carry out a prepared visit with no signal), OFF-4 (what is waiting), OFF-5 (sync by itself and on demand), OFF-6 (interrupted uploads resume), OFF-7 (syncing twice changes nothing), OFF-8 (local copies go only after the server confirms), OFF-9 (the unprepared-visit warning), OFF-11 (conflicts keep the device's copy for export), the conflict codes of TRD §7.4, `visit.sync_conflict`, and the warnings in the reschedule, cancel and change-owner dialogs when a visit is prepared on a phone. Journey J6 end to end. Depends on W13 (prepared bundles, the PIN session, the `outbox` and `blobs` tables, the upload engine).

**Not in W14:** the field test on real phones (W15), reports (Phase 6), Background Sync (question 3), editing a visit's plan offline (OFF-10).

## 1. Where things stand (checked 2026-10-22)

- **Server:** there is no `POST /api/v1/sync` and no `sync_operations` collection. What exists was written to be reused: every board and lifecycle route is idempotent by a device-made ID or by "the same person making the same move again" (W10-8, W11), the domain raises exactly the codes `/sync` reports (`not_attending`, `not_owner`, `not_editor`, `not_started`, `visit_cancelled`, `already_ended`, `locked`, `element_changed`, `element_deleted`, `duplicate_id`), `POST /visits/{id}/restore` exists, and `/internal/attachable` already accepts an upload for an element whose create op has not synced yet (W11-27), so a phone may upload before it applies ops.
- **Phone:** `outbox` and `blobs` exist, empty. The upload engine (`offline/upload.ts`: resumable 8 MiB parts, `parts_done`) works but is driven from memory by `useVisitMedia` and `uploadQueues`. The board UI (`VisitBoard`, `ElementDialog`) and the visit moves (`useVisitMoves`) call the server and show what it answers. `prepared_on` is written and read; no dialog warns about it yet.
- **Findings that bind:** F8 (queued ops outlive app versions), F11 (one sync runner at a time), F12 (iOS stops JavaScript in the background), F6 (Playwright and WebKit).

## 3. Decisions (proposed W14-1 to W14-14)

1. **`POST /api/v1/sync` is a dispatcher, not a second implementation.** Body `{device_id, ops: [{op_id, v, type, visit_id, payload}]}`, at most 100 ops, in the order the phone sends them. Each op is run by calling the route function that already does the work (`add_element`, `save_element`, `arrive`, …) with the caller's `User` and `Ctx`, so scoping, roles, validation, events and the outbox are the same code as online (rules 2 to 6). Roles: technicians and admins (viewers 403).
2. **One answer per op:** `applied`, `duplicate`, `conflict` (with `code`, a message and, where there is one, `current`: the server's copy) or `error` (a message; the phone retries). Mapping from what the routes raise: a `Conflict` or `Forbidden` whose code is in the TRD §7.4 table (and the `not_attending`, `not_started` family) is a `conflict`; `ValidationFailed` is a permanent `error` the person must see; anything else is a retryable `error`. A **failed op stops the later ops of the same visit** (answered `skipped`), not other visits' (TRD §7.3).
3. **`sync_operations`** (`_id` = `op_id`, `user_id`, `device_id`, `type`, `visit_id`, `result`, `applied_at`, TTL 90 days; BSD) stores each answer, so asking again returns it with `duplicate: true` at once. It is written after the op's own transaction: the ops are already safe to repeat (device-made IDs, same-person moves are no-ops), so the worst a crash between the two can do is run the op again and get `duplicate`. A different user using a known `op_id` is refused.
4. **The op types are TRD §7.2:** `visit.start`, `station.arrive`, `station.depart`, `element.create`, `element.update`, `element.delete`, `element.media_add`, `element.media_remove`, `visit.end`. Every op carries `v` (payload version, F8): the server accepts the current and the previous version and answers `error: update_required` (retryable after an app update) for a newer one. The payloads are the existing request bodies plus `at` (the device's time, already checked within 5 minutes ahead and 30 days back).
5. **`visit.sync_conflict`** (visit facts, `reason`, `user_id`, `op_types[]`; never the content) is emitted once per visit and reason per sync run, in the same transaction as the `sync_operations` writes. Platform turns it into an in-app notification for the lead and every admin ("Work recorded on a cancelled visit", "Devon's work on WXR-012 came back as a conflict"); no email in W14. For `visit_cancelled` an admin restores the visit (`POST /visits/{id}/restore`, exists) and the next sync applies what waits.
6. **Local-first for a prepared visit** (question 1). When a visit is prepared on this phone by this user, every board write and every move goes to Dexie first, in one transaction with its outbox op, and the runner sends it at once when there is a connection. There is one path, so a phone that drops signal half-way cannot reorder its own changes. A visit that is not prepared keeps the direct calls and says so when started (OFF-9).
7. **The working copy is element-shaped.** Elements live in the `visits` table, one row per element (`id` = element id; `visit_id`, `station_id`, `user_id`, the `BoardElement` as the board shows it, `base_version`, `dirty`), seeded from the bundle and replaced by the server's copy when an op is applied. Local copies are built by one pure module (`features/visits/localBoard.ts`) that mirrors the server's content rules (title required, items, priority, sharing defaults, `can_edit`) well enough for the screen; the server stays the judge (`ValidationFailed` comes back as an error on the op).
8. **Dexie version 2** adds indexes to `visits` (`[visit_id+station_id]`) and `outbox` (`[user_id+status]`), with an upgrade that touches no row of `outbox` or `blobs` and a Vitest upgrade test from a version 1 database holding both (offline-data.md §1).
9. **One transaction for a user action:** the element (or move), its outbox op and, for a file, its `blobs` row are written together or not at all. Hashing, resizing and reading EXIF come **before** the transaction (no foreign await inside it).
10. **The runner** (`offline/sync.ts`, no Vue, no DOM): under the Web Lock `mms-sync` with `ifAvailable` (F11), refresh under `mms-auth-refresh` (a failed refresh means "Log in to finish syncing", the queue stays), for each visit in `seq` order: upload the blobs its next ops need, then send up to 100 ops; apply the answers in one Dexie transaction each (delete the op and, for `applied` and `duplicate`, mark the element clean; keep the op with `status: conflict` and the server's `current` for a conflict; `attempts++` and backoff for a retryable error). Backoff is 2 s doubling to 5 minutes with jitter, reset by success or **Sync now**. A failed network request is "offline", whatever `navigator.onLine` says.
11. **Triggers:** the app starting, the `online` event, the app returning to the foreground, every 5 minutes while online and open, and **Sync now**; at once after each local write when online. Overlaps are harmless (the lock). The runner is written free of Vue so the service worker can run it from a Background Sync event later (question 3).
12. **Uploads resume from the phone.** A blob's `upload_id` and `parts_done` are saved after each part; the engine in `offline/upload.ts` gets a Dexie-backed store. `POST /uploads` is idempotent by `media_id` and joins an open upload (F15), and the store of parts at the files host is the truth, so a lost ETag cannot matter. The `element.media_add` op waits in the queue until its file has been `complete`d; a file that media is still checking (409 `file_not_ready`) is a retryable error. **Local copies go only after the server confirms** (OFF-8): a blob after its `media_add` is `applied` or `duplicate`; a visit's bundle, files and element copies after its `visit.end` is applied and nothing for it is left.
13. **A conflict keeps the device's copy and offers Export.** The op stays with its reason and the server's copy; the element stays on the phone as the person left it, marked "Not saved". **Export** (question 2) writes one JSON file for the visit's conflicted work (elements, items, captions, times) and shares the media files with the phone's share sheet where it exists, or downloads them. Nothing is removed until the person says "Done with this" (it is removed locally, after Export has been offered once) or an admin resolves it on the server and the next sync applies. A conflict never blocks other visits' ops.
14. **Warnings for people planning.** `prepared_on` (W13) drives one sentence in the Reschedule, Cancel and Change owner dialogs: "This visit is prepared on Devon Brown's phone. Work not yet synced from it may come back as a conflict." (shown to the lead and admins, staff only).

## 6. PWA pre-flight (answers)

1. **Device.** iOS floor: no Background Sync (not planned), JavaScript stops in the background (F12: the page says "Keep the app open", takes a wake lock where it can, and a paused upload resumes next time), storage may be cleared (F3: shown). Chrome and Edge get the same code.
2. **Network.** Every request can die half-way: the op is deleted only after its answer is stored; a blob part is saved after it lands; `complete` and `media_add` repeat safely; a refresh that fails keeps the queue.
3. **Lifecycle.** Queued ops keep their `v`; the server takes two versions (F8); Dexie version 2 is additive and tested from version 1 with a full `outbox`; an update is not applied while the runner holds the lock or a capture is writing (the update store is told, as for Prepare).
4. **Data and loss.** The device copy is deleted only after the server confirms (OFF-8); a conflict keeps both; logout keeps `outbox` and `blobs` for that user and nobody else can sync them (tested with two users). The failure injected: a throw inside a transaction leaves neither element nor op; a quota error on a capture leaves nothing half-written.
5. **Storage.** 50 photos and 3 videos is the design load; capture checks free space first and `persist()` was asked at Prepare. A file is stored once, as a blob, and uploaded from there.
6. **Caching.** Nothing new: no API response is cached; the runner uses fetch and the worker never sees it. No new file in the precache (the budget is 29 of 30: the runner and the board changes join the `app` chunk).
7. **Security and shared devices.** No token in storage (the runner takes one under the refresh lock and keeps it in memory); every Dexie read filters by `user_id`; an export holds only the person's own work; CSP unchanged (a `blob:` object URL for sharing is allowed).
8. **Proof.** Vitest with fault injection (throw mid-upload, expire the token, quota error, kill a transaction, same batch twice, two users); API tests including a property test (a batch twice leaves the same state and the same answers); Playwright in Chromium with `setOffline` for J6 (prepare, go offline, capture, restart and unlock, sync, count every record and file on the server, sync again and nothing changes), and **an attempt at WebKit** (finding F6) to decide whether the flow runs there with the worker or without it. Real devices: the W15 field test.

## 8. Questions for you (answered 2026-10-22: the defaults stand)

1. **Local-first or online-first for a prepared visit?** Default: **local-first** (decision 6): one path, no reordering, every step is saved on the phone first. Alternative: use the server directly while online and the outbox only offline, which keeps today's screens but needs two paths and an ordering rule for the moment the signal returns.
2. **What does Export produce?** Default: one JSON file per conflicted visit plus the media files, through the phone's share sheet (or downloads where sharing is not available). Alternative: a single zip (needs a library in the precache budget or a worker) or a PDF summary (Phase 6).
3. **Background Sync on Android?** Default: **not in W14**. It helps only on Chrome, iOS has none, and the field test uses both; the runner is written so it can be added. Alternative: add the `sync` event to the worker now (inside `sw.js`, no new file).
4. **WebKit under Playwright (F6).** Default: try it in slice 4; if the service worker does not run there, the WebKit run covers the Dexie and runner flow without it and the iPhone stays the only full proof. Alternative: skip WebKit and rely on the iPhone in W15.
